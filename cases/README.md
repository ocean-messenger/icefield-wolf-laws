# 案例库

## 免责声明

本案例库是所有读者的自由思考区。

在这里分享的内容，全部是读者自己的感悟和运用。
项目维护者没有参与任何具体案例的发言和思考。

如果某位读者从狼群故事中学到了什么，那是这位读者自己厉害。
如果某位读者把学到的用在了自己的领域，那也是这位读者自己的事。

本项目只提供故事，不提供结论。
本项目只提供法则，不提供用法。
本项目只提供案例，不提供评判。

所有案例仅代表投稿者个人观点，不代表本项目立场。

---

## 结界：禁止讨论区

以下话题一律不得在案例库中出现，包括但不限于：

- 社会制度比较
- 历史规律总结
- 历史运动评价
- 国际局势分析
- 现行政策评论
- 任何国家、政党、领导人的直接评价
- 任何民族、宗教、种族的比较
- 任何涉及现实政治人物的类比
- 其他可能引发对立、争议、或超出项目范围的宏大叙事

一旦出现，PR 直接关闭，不讨论、不解释、不妥协。

这不是审查，这是保护。保护这个项目能活下去，保护投稿者不被牵连。

---

## 我们鼓励什么

我们鼓励从**当时完整的情境**出发，分析一个合作系统内部发生了什么。

就像高中写议论文那样：

- 可以分析“为什么我们需要这样合作”
- 可以分析“为什么这个团队会散”
- 可以分析“为什么这个决策会崩”

但我们**不做**以下事情：

- 不上升层次到“阶级就是剥削”
- 不上升层次到“历史必然规律”
- 不上升层次到“某种制度必然灭亡”

分析可以深，但层次不能太高。
就事论事，就团队论团队，就案例论案例。

---

## 推荐机制（不是淘汰机制）

案例库不是考试，没有及格线。

- 所有不越界的投稿都会被保留
- 大家觉得好的案例，会被推荐到显眼位置
- 大家觉得一般的案例，也保留在库里，作为素材
- 甚至，差的案例可以作为“驳论文素材”存在

我们不淘汰差的见解。
差的见解只要不越界，它自有它的用处：
它鼓励了投稿积极性，它甚至能够作为素材写驳论文。

**推荐机制**：

- 用 GitHub 的 👍 / 👎 reaction 表达态度
- 👍 多的，被推荐到 `featured/` 目录
- 👎 多的，留在 `submitted/`，但不会删除
- 如果有人愿意写反驳文章，反驳文章本身也可以作为新案例投稿

---

## 案例格式

每个案例建议包含（但不强制）：

1. **案例背景**：发生了什么
2. **外部触发**：表面原因是什么
3. **内部过程**：用本框架解释，内部发生了什么
4. **对应机制**：对应故事里的哪条推论或哪幅图
5. **一句话总结**

不要求完美，不要求成熟。
只要不越界，就可以投。

# 投稿流程（详细版）

## 一、先搞清楚：投稿 = 提 Pull Request

GitHub 不是论坛，不能直接发帖。
投稿的方式是：**把你的案例写成一个文件，然后申请合并到本仓库。**

这个“申请合并”的动作，就叫 **Pull Request（简称 PR）**。

流程大概是：

```
Fork 本仓库
    ↓
在你的 Fork 里新建文件
    ↓
提交
    ↓
发起 Pull Request
    ↓
社区在 PR 里评论、投票
    ↓
维护者合并 → 你的案例进入本仓库
```

下面一步步来。

---

## 二、第一步：Fork 本仓库

1. 打开本仓库首页。
2. 点右上角的 **`Fork`** 按钮。
3. 等几秒，GitHub 会在你的账号下复制一份一模一样的仓库。
4. 复制完之后，你会自动跳转到你自己的 Fork。

**Fork 是什么？**
就是“拷贝一份到自己家”。你在自己家的改动，不会直接影响本仓库。等你改好了，再通过 PR 申请合并回来。

---

## 三、第二步：在你的 Fork 里新建案例文件

1. 在你的 Fork 首页，点 **`Add file`** → **`Create new file`**。
2. 文件名框里输入：

   ```
   cases/submitted/案例名-你的ID.md
   ```

   举个例子，如果你叫 `wolf123`，想写泰坦尼克号：

   ```
   cases/submitted/泰坦尼克号-wolf123.md
   ```

   **注意**：
   - 一定要放在 `cases/submitted/` 目录下
   - 文件名不要有空格，用 `-` 连接
   - 后缀是 `.md`（Markdown 格式）

3. 在下面的大编辑框里，写你的案例。推荐按这个模板写：

   ```markdown
   # 案例：泰坦尼克号

   ## 1. 案例背景

   1912年，泰坦尼克号在北大西洋撞上冰山沉没。

   ## 2. 外部触发

   表面原因：撞上冰山。

   ## 3. 内部过程

   用狼群法则来看：
   - 收到多次冰山警告，但关键信息没有传到船长手里
   - 救生艇数量按“美观”设计，而不是按“安全”设计
   - 撞冰山后，指挥链条混乱

   ## 4. 对应机制

   - 推论四：信息不完备
   - 推论六第三条：纠错失效

   ## 5. 一句话总结

   冰山只是敲了门，真正开门的是内部结构。
   ```

4. 写完之后，往下划，点 **`Commit changes...`**。
5. 弹窗里点 **`Commit changes`**。

---

## 四、第三步：发起 Pull Request

1. 提交完之后，回到你的 Fork 首页。
2. 你会看到一条提示：

   > “This branch is 1 commit ahead of abyssal-incoker:main.”

3. 旁边有一个绿色按钮 **`Contribute`** → 点它 → 选 **`Open pull request`**。
4. 进入 PR 页面，填写：
   - **标题**：比如 `投稿：泰坦尼克号-wolf123`
   - **说明**：简单说一句你投了什么，比如“用推论四和推论六分析了泰坦尼克号”
5. 点 **`Create pull request`**。

**到这里，投稿就完成了。**

---

## 五、第四步：等社区评论和投票

你的 PR 会出现在本仓库的 `Pull requests` 标签里。

所有人都可以：
- 在 PR 里评论
- 在 PR 里点 👍 / 👎
- 提出修改意见

如果 👍 多，说明大家觉得这个案例好。
如果 👎 多，说明大家觉得一般，但只要不越界，PR 不会被关闭，案例也会被保留。

---

## 六、第五步：合并

- 如果大家觉得好，维护者会点 **`Merge`**，你的案例正式进入本仓库 `cases/submitted/`。
- 如果 👍 特别多，可能会被移到 `cases/featured/`，成为“推荐案例”。
- 如果越界，PR 会被 **`Close`**，不合并。

---

## 七、投稿后的去向

| 状态 | 文件在哪里 |
|------|-----------|
| PR 还没合并 | 在你的 Fork 里，PR 页面能看到 |
| PR 被合并 | 本仓库 `cases/submitted/` |
| 被推荐 | 本仓库 `cases/featured/` |
| 越界被关闭 | 不进入本仓库，PR 关闭 |

---

## 八、如果你不想用 GitHub 怎么办

GitHub 对非程序员确实有点门槛。

如果你不会用 GitHub，但想投稿，可以：

1. 去本仓库的 `Discussions` 区，发一个帖子，标题写 `【投稿】你的案例名`。
2. 在帖子里写你的案例。
3. 如果有志愿者愿意帮你转成 PR，他们会帮你。

**我们不拒绝任何不越界的投稿，只是 GitHub 的流程需要有人帮你跑一遍。**

---

## 九、复审机制

- 任何人可对 `featured/` 里的案例发起 issue，提出异议
- 异议有理有据的，重新进入讨论
- 讨论后，由社区决定是否移回 `submitted/`

---

## 十、目录结构

```
cases/
├── README.md          ← 本文件
├── featured/          ← 大家推荐的好案例
├── submitted/         ← 所有不越界的投稿
└── rejected/          ← 越界被关闭的（仅留记录）
```
